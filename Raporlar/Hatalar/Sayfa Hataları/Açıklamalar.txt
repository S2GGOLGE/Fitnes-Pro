# Fitness Pro — UI/UX Hata Analizi ve Düzeltme Raporu

## 1. Login — E-posta Doğrulama Modalının Açılmaması

**Referans:** Login e-posta doğrulama akışı  
**Öncelik:** Yüksek

### Mevcut Sorun
Login ekranındaki e-posta doğrulama modalı, açılması gereken durumda görüntülenmemektedir. Modalın açılmaması; kullanıcı etkileşimi, JavaScript/React state yönetimi, doğrulama akışı veya modal bileşeninin koşullu render edilmesiyle ilgili bir sorundan kaynaklanabilir.

Sorunun gerçek nedeni kod incelenmeden kesin olarak belirlenmemelidir.

### İncelenecek Alanlar
- Login bileşenindeki e-posta doğrulama modalını açan fonksiyon ve tetikleyici koşullar.
- Modalın görünürlüğünü kontrol eden state değişkenleri ve bunların güncellenme sırası.
- Login API yanıtının e-posta doğrulaması gerektiğini belirten durumlarla doğru eşleştirilmesi.
- API yanıtının frontend tarafından doğru işlenip işlenmediği.
- Modalın koşullu render edilmesi, bileşen yaşam döngüsü ve olası erken dönüşler.
- JavaScript konsol hataları ve ağ sekmesindeki başarısız istekler.
- CSS `display`, `visibility`, `opacity`, `z-index` ve `overflow` gibi özelliklerin modalın görünürlüğünü engelleyip engellemediği.
- Modalın başka bir bileşen tarafından kapatılması veya görünürlük state'inin sıfırlanması.
- E-posta doğrulama kodu gönderme ve yeniden gönderme akışının modalın açılmasından doğru şekilde ayrıştırılması.

### Beklenen Düzeltme
1. Modalın açılmasını engelleyen kök neden belirlenmelidir.
2. Gerekli durumda modalın güvenilir ve tutarlı şekilde açılması sağlanmalıdır.
3. API yanıtları mevcut backend sözleşmesine uygun olarak işlenmelidir.
4. Modalın açılması için gereksiz veya hatalı koşullar varsa düzeltilmelidir.
5. E-posta doğrulama kodu gönderme, kod girme, doğrulama ve hata mesajı akışları korunmalıdır.
6. Modalın kapatılması ve yeniden açılması doğru çalışmalıdır.
7. Mevcut CSS ve tema sistemiyle uyumlu görünüm sağlanmalıdır.

### Test Senaryoları
- E-posta doğrulaması gereken bir hesapla giriş yapıldığında modal açılmalıdır.
- Normal giriş yapan ve doğrulaması tamamlanmış bir hesapta mevcut giriş akışı bozulmamalıdır.
- API hatası durumunda uygun hata mesajı gösterilmelidir.
- Modal kapatılıp tekrar açıldığında state tutarsızlığı oluşmamalıdır.
- Kod gönderme, yeniden gönderme ve doğrulama işlemleri çalışmalıdır.
- Sayfa yenileme veya tekrar giriş işlemleri mevcut kimlik doğrulama mimarisini bozmamalıdır.

**Önemli:** Modalın açılmaması yalnızca CSS düzenlemesiyle geçiştirilmemeli; sorunun state yönetimi, API yanıtı veya render koşullarından kaynaklanıp kaynaklanmadığı doğrulanmalıdır.

## 2. Password Input — Göster/Gizle İkonlarının Uyumsuzluğu

**Referans:** Görsel 3 — Login Şifre Güncelleme Modalı  
**Referans:** Görsel 4 — Register Şifre Alanları  
**Öncelik:** Orta

### Mevcut Sorun
Login şifre güncelleme modalındaki ve Register ekranındaki parola inputlarında kullanılan göster/gizle ikonları tutarsızdır. İkonların görsel durumu, biçimi veya etkileşim davranışı beklenen kullanıcı deneyimiyle uyuşmamaktadır.

### İstenen İkon Davranışı

| Parola durumu | Input tipi | Gösterilecek ikon |
|---|---|---|
| Parola gizli | `type="password"` | Açık göz ikonu |
| Parola görünür | `type="text"` | Kapalı göz ikonu |

**Beklenen davranış:** Kullanıcı parola gizliyken açık göz ikonunu görmelidir. İkona tıkladığında parola görünür hâle gelmeli ve ikon kapalı göze dönüşmelidir. Tekrar tıklandığında parola gizlenmeli ve ikon açık göze dönmelidir.

### 2.1. Login — Şifre Güncelleme Modalı
- Modal içerisindeki tüm parola inputlarının göster/gizle kontrolleri incelenmelidir.
- İkonlar, projenin mevcut ikon kütüphanesi ve tasarım standardıyla uyumlu hâle getirilmelidir.
- İkonun görünümü, inputun mevcut parola görünürlüğü durumuyla senkronize olmalıdır.
- Parola görünürlük değişiminde input değeri korunmalıdır.
- İkonun konumu, boyutu, rengi ve tıklama alanı input tasarımıyla uyumlu olmalıdır.
- Açık ve koyu tema renkleri korunmalıdır.

### 2.2. Register — Şifre Alanları
- Kayıt formundaki parola ve parola tekrar alanları ayrı ayrı kontrol edilmelidir.
- Her inputun görünürlük durumu bağımsız yönetilmelidir.
- Bir inputun ikonuna tıklamak diğer inputun görünürlük durumunu değiştirmemelidir.
- Açık göz ve kapalı göz ikonları tüm alanlarda aynı görsel standardı izlemelidir.
- Parola kuralları, parola eşleşme kontrolü ve kayıt validasyonu etkilenmemelidir.

### Teknik Uygulama Gereksinimleri
- Projede kullanılan mevcut ikon kütüphanesi tercih edilmelidir; yeni bir paket eklenmemelidir.
- İkonlar, parola görünürlüğünü yöneten state üzerinden belirlenmelidir.
- İkon butonları formu yanlışlıkla göndermemelidir (`type="button"`).
- Klavye ile kullanım ve erişilebilir adlandırma desteklenmelidir.
- Inputun sağ iç boşluğu, ikonun metinle çakışmasını önleyecek şekilde düzenlenmelidir.
- İlgisiz parola doğrulama veya kimlik doğrulama mantığı değiştirilmemelidir.

### Kabul Kriterleri
- Parola gizliyken açık göz, görünürken kapalı göz ikonu gösterilir.
- İkon davranışı Login şifre güncelleme modalında ve Register ekranında tutarlıdır.
- Register alanlarının görünürlük durumları birbirinden bağımsızdır.
- Parola değerleri ve form işlemleri etkilenmez.
- Açık ve koyu tema görünümü korunur.

## 3. Mesaj İsteği Ayarları — Dark/Light Tema Uyumsuzluğu

**Referans:** Görsel 1  
**Öncelik:** Orta

### Mevcut Sorun
Mesaj isteği ayarları ekranında bazı bileşenler seçili tema ile uyumlu görüntülenmemektedir. Açık tema seçiliyken koyu tema renkleri kalan alanlar veya koyu temada yanlış renk kullanan bileşenler, ekranın görsel bütünlüğünü bozmaktadır.

### İncelenecek Alanlar
- Mesaj isteği ayarları ekranının ana kapsayıcısı.
- Ayar kartları, arka planlar ve kenarlıklar.
- Başlıklar, açıklama metinleri ve etiketler.
- Seçenekler, radio/checkbox bileşenleri veya varsa özel seçim kontrolleri.
- Toggle/switch kontrolleri ve seçili/seçili olmayan durumları.
- Hover, focus, disabled ve aktif durum renkleri.
- Modal, dropdown veya diğer alt bileşenler varsa bunların tema davranışı.
- Tema değişkenleri ile bileşenlere uygulanan CSS sınıfları arasındaki uyum.

### Beklenen Düzeltmeler
1. Referans görselde uyumsuz görünen bileşenler belirlenmelidir.
2. Bileşenlerin sabit renkler yerine mümkün olduğunca projenin mevcut tema değişkenlerini kullanması sağlanmalıdır.
3. Açık temada arka plan, metin, kenarlık, ikon ve seçim kontrolü renkleri açık tema tasarımına uygun olmalıdır.
4. Koyu tema seçildiğinde mevcut koyu tema tasarımı korunmalıdır.
5. Tema değişikliği sonrasında ayarların seçili durumları ve kullanıcı tercihleri değişmemelidir.
6. CSS specificity veya inline stil kaynaklı çakışmalar tespit edilerek düzeltilmelidir.
7. Aynı CSS veya bileşen altyapısını kullanan başka alanlarda benzer sorun olup olmadığı kontrol edilmelidir.

### Kabul Kriterleri
- Mesaj isteği ayarları hem açık hem koyu temada tutarlı görünmelidir.
- Metin ve arka plan kontrastı yeterli olmalıdır.
- Seçili ayarlar, toggle durumları ve kullanıcı tercihleri korunmalıdır.
- Tema değiştirmek ayarları sıfırlamamalı veya backend verilerini değiştirmemelidir.
- Düzeltme, ilgisiz sayfaların tasarımını etkilememelidir.

## 4. Genel Uygulama Kuralları

1. Değişiklik yapmadan önce ilgili frontend bileşenleri, CSS dosyaları, tema sistemi ve API entegrasyonları incelenmelidir.
2. Her hata için önce kök neden tespit edilmeli, ardından en küçük kapsamlı düzeltme uygulanmalıdır.
3. Backend API sözleşmaları ve çalışan iş mantığı gereksiz yere değiştirilmemelidir.
4. Yeni ikon veya CSS kütüphanesi eklenmemelidir.
5. Mevcut tasarım dili ve renk paleti korunmalıdır.
6. İlgisiz dosyalarda değişiklik yapılmamalıdır.
7. Build/lint kontrolleri ve ilgili regresyon testleri çalıştırılmalıdır.
8. Sonuç raporunda her hata için kök neden, değiştirilen dosyalar, uygulanan düzeltme ve test sonuçları belirtilmelidir.
