1. YARIŞ KOŞULLARI (RACE CONDITIONS)
====================================

1.1 [YÜKSEK] Çift submit → paralel refreshLoginRateStatus
    LoginEndpoint.js:149-184 — submit handler async, await refreshLoginRateStatus()
    çağrısı içinde. Kullanıcı submit butonuna hızlıca iki kez basarsa (veya
    çift tıklama / enter iki kez) iki paralel istek başlar. İkisi de aynı
    network çağrısını yapar, ikisi de aynı sonucu alır, ama her ikisi de
    ayrı ayrı applyTemporaryLock / clearRateLimit çağırır. Çift interval
    kurulabilir, sonra clearRateCountdown ile silinir, ama arada görsel
    titreme olabilir.
    İlk satırda submitButton.disabled = true (loading state) yapıldığı
    için büyük ölçüde engellenmiş. ANCAK disabled olmadan önceki bir
    senkron boşluk ve HTML5 native form invalid durumunda bu koruma
    çalışmaz. EK OLARAK: refreshLoginRateStatus başarısız olduğunda
    finally içinde disabled = false yapılıyor; bu noktadan sonra 2.
    tıklama yeni bir submit tetikler.
    ÇÖZÜM: Submit handler girişinde bir "inFlight" flag'i tut, tekrar
    girişleri erken return et.

1.2 [ORTA] Login response ile pre-check refresh yarışması
    Submit handler sırası:
      1) await refreshLoginRateStatus()      → getLoginRateStatus()
      2) if (isActive()) return               → karar
      3) fetch(LOGIN_ENDPOINT) ...            → POST
    Eğer 1. adımda backend normal dönüyor ve 3. adım gönderilmeden hemen
    önce backend tarafında rate-limit tetiklenirse (örn. paralel başka
    sekmeden gelen başarısız login), 3. adım backend tarafından reddedilir
    ve response rateLimited:true gelir. Bu doğru çalışır (LoginEndpoint.js
    2. dalı yakalar). AMA: pre-check 1. adımda backend zaten "rateLimited"
    dönüyorsa, 2. adımda return edilir ve POST hiç gönderilmez — bu
    promptun 3. maddesinde istenen davranış. Yarış burada yok. Sorun yok.
    NOT: Yarış penceresi küçük ama 1.1'deki çift submit ile birleşirse
    iki paralel POST gönderilebilir.

1.3 [ORTA] Interval callback içinde async/await — exception fırtınası
    LoginRateLimitUI.js:182-195 — setInterval(async () => { ... await
    refreshLoginRateStatus(); ... }, 1000). refreshLoginRateStatus
    içindeki fetch başarısız olursa exception fırlatır, ama setInterval
    callback'i async olduğu için bu exception "unhandled promise
    rejection" olarak çıkar. Tarayıcı konsolu kirlenir, diğer interval
    tick'leri etkilenmez (clearRateCountdown zaten çağrıldı). Pratik
    etkisi düşük ama production'da izleme/log sistemleri için sorun.
    ÇÖZÜM: interval callback'inde try/catch veya refresh'i fire-and-forget
    pattern ile sarma.

1.4 [DÜŞÜK] 1 saniyelik redirect yarışı
    LoginEndpoint.js:498-506 — başarılı login sonrası setTimeout(() => {
    window.location.href = "index.html"; }, 1000). Bu sürede kullanıcı
    başka bir sekmeye geçebilir, sayfayı kapatabilir veya form alanlarına
    yazabilir. setTimeout iptal edilmez. location.href atandığı an navigasyon
    başlar; yarım kalmış UI state'i (örn. alert mesajı) görünmeyebilir.
    Kabul edilebilir UX davranışı, bug değil. Sadece not.


2. TUTARSIZ STATE (STATE INCONSISTENCY)
=======================================

2.1 [YÜKSEK] finally bloğu + form.rate-limited class senkronizasyonu
    LoginEndpoint.js:544-579 (finally), LoginRateLimitUI.js:285-318
    (setLoginFormDisabled).
    finally içinde buton yönetimi sadece submitButton.disabled'a bakar:
      - isActive() → text düzelt, disabled'a dokunma
      - isPermanentLockActive() → text düzelt, disabled = true
      - aksi → disabled = false, text düzelt
    AMA setLoginFormDisabled(true) form üzerine 'rate-limited' class'ı
    koyar (CSS display:none), username/password/forgotPassword/toggle
    butonlarını disabled yapar. finally'de SADECE submit button
    restore ediliyor; diğer input'lar kilitli kalıyor.
    Edge case: refreshLoginRateStatus network hatası döner ve catch
    bloğu mevcut state'i korur, sonra finally çalışır. isActive() false
    + isPermanentLockActive() false → submitButton.disabled = false,
    text düzeltilir. AMA form.rate-limited class hâlâ orada (önceki
    kilitli state korunduğu için). Kullanıcı submit'e basabilir mi?
    Hayır, çünkü buton display:none. Ama DOM hackleyerek veya JS'i
    devre dışı bırakarak gönderebilir.
    ÇÖZÜM: finally içinde setLoginFormDisabled(false) ile form tamamen
    sıfırlansın, ya da bu sınıf senkronizasyonu tek bir yerden yönetilsin.

2.2 [ORTA] Login response'ta accountLocked=true + pre-check farkı
    Pre-check (refreshLoginRateStatus) accountLocked:true dönüyorsa
    LoginRateLimitUI.showPermanentLock çağrılır → form disable, buton
    disable. Submit handler'da mevcut isActive / isPermanentLockActive
    kontrolleri yakalar. Tamam.
    AMA: Eğer pre-check normal dönüyor, login POST gönderiliyor, backend
    accountLocked:true dönüyorsa (örn. pre-check ile login POST arasında
    başka sekmeden 15 başarısız deneme olduysa), LoginEndpoint.js 1.
    dalı yakalıyor ve showPermanentLock çağrılıyor. Tamam.
    Sorun yok. Sadece not.

2.3 [ORTA] permanentLockActive + isActive çakışması
    LoginRateLimitUI.js:422, 376 — applyTemporaryLock
    permanentLockActive=false yapar. applyPermanentLock true yapar.
    AMA: Eğer kalıcı kilit aktifken (permanentLockActive=true, rateCountdownTimer=null)
    refreshLoginRateStatus tekrar çağrılırsa ve backend hâlâ
    accountLocked:true dönüyorsa applyPermanentLock tekrar çağrılır
    (permanentLockActive tekrar true olur) — aynı sonuç, sorun yok.
    Eğer backend accountLocked:false ama rateLimited:true dönüyorsa
    applyTemporaryLock → permanentLockActive=false. Kalıcı kilit UI'ı
    kalkmış olur. Tutarlı.
    Edge case: Backend accountLocked:true + rateLimited:true gönderirse
    (anlamsız ama mümkün), 1. dal önce yakalanıyor, applyPermanentLock
    çağrılıyor. Tamam.

2.4 [ORTA] getRemainingSeconds() in-memory ama API sözleşmesi
    LoginRateLimitUI.js:478-480 — getRemainingSeconds currentRemaining
    döner. Eski API'de localStorage'dan "until" timestamp okuyordu
    (kalan süre hesaplanıyordu). Yeni davranışta sadece in-memory
    değişken. Eğer iki farklı sekme açıksa ve birinde timer 250'den
    geri sayıyorsa, diğer sekme hâlâ 287 görüyor (çünkü init'te
    kendi backend response'unu aldı). Her sekme kendi sayacını tutar.
    Tasarım gereği doğru (kullanıcı talebi: backend tek otorite), ama
    multi-tab UX'i tutarsız. Kabul edilebilir.

2.5 [ORTA] applyTemporaryLock clearAlert() — alert mesajı kaybı
    LoginRateLimitUI.js:450 — applyTemporaryLock içinde clearAlert()
    çağrılır. Bu, backend'in daha önce gönderdiği ve formAlert'a yazılan
    alert mesajını siler. Eğer kullanıcı submit etti, login POST başarısız
    oldu, showAlert ile "Kullanıcı adı veya şifre hatalı" mesajı
    gösterildi, sonra refreshLoginRateStatus tetiklendi (örn. login
    handler'ın catch'inde veya başka yerden), applyTemporaryLock
    çağrıldı, alert silindi. Kullanıcı bilgilendirme kaybı.
    ÇÖZÜM: applyTemporaryLock içinde lock UI mesajı zaten
    loginRateLimitMessage'a yazılıyor. clearAlert() gereksiz. Kaldırılabilir.

2.6 [DÜŞÜK] isActive() vs timerIntervalId vs visible timer text
    LoginRateLimitUI.js:469-474 — isActive sadece rateCountdownTimer !== null
    kontrol eder. Eğer interval herhangi bir nedenle temizlendiyse
    (örn. startRateCountdown(0) içindeki clearRateCountdown + return),
    isActive false döner, ama DOM'daki timer text hâlâ eski süreyi
    gösterebilir. UI ile mantık state'i arasında küçük tutarsızlık
    penceresi.


3. GÜVENLİK AÇIKLARI
====================

3.1 [YÜKSEK] JWT localStorage'da → XSS ile çalınabilir
    auth.js:22-23, 25 — token ve user objesi localStorage'a yazılıyor.
    XSS saldırısıyla saldırgan document.localStorage okuyabilir.
    Fitness Pro'da henüz XSS vektörü görünmüyor, ama kullanıcı adı gibi
    alanlar DOM'a textContent ile yazılıyor (auth.js syncAuthUI),
    innerHTML kullanılmıyor (LoginEndpoint.js başarılı login'de
    showAlert(textContent) kullanıyor). Yine de HttpOnly cookie
    taşımaya geçiş önerilir.
    ÖNERİ: Backend'in Set-Cookie ile HttpOnly + SameSite=Strict cookie
    geçirmesi, frontend'in yalnızca user display için localStorage
    kullanması (token'sız).

3.2 [ORTA] JWT decode'da atob + decodeURIComponent
    auth.js:90-95 — atob() ve decodeURIComponent() kullanılıyor.
    parseJwt try/catch ile sarılmış, hata durumunda null dönüyor.
    Pratikte güvenli. AMA: Gelen payload beklenenden büyükse bellek
    sorunu olabilir. Ciddi bir saldırı vektörü değil, sadece hardening.

3.3 [ORTA] Token expired kontrolü isTokenExpired
    auth.js:105-111 — decoded.exp < currentTime kontrolü. exp claim
    yoksa (decoded.exp undefined) false döner → token expired değil
    kabul edilir. Bazı backend varyantlarında exp olmayabilir, bu durumda
    token süresiz kabul edilir. Tehlikeli.
    ÇÖZÜM: exp yoksa token'ı expired kabul et veya backend tarafında
    exp zorunlu kıl.

3.4 [ORTA] auth/me endpoint'i token verify sonrası 401
    auth.js:181-184 — 401 alındığında logout(true) çağrılıyor,
    YANİ return response (response objesi döner, false değil). Çağıran
    authFetch.then(response => ...) zincirinde response.ok false olduğu
    için normal HTTP hata muamelesi görür. Ama logout zaten tetiklendi.
    İyi tasarım. ÇÖZÜM YOK, sadece not.

3.5 [ORTA] getUser() fallback → token decode
    auth.js:62-72 — localStorage'da user yoksa token decode edilip user
    çıkarılıyor. Bu, token içeriğinin userId, username, role alanlarını
    içerdiğini varsayıyor. Token imzası doğrulanMıYOR (frontend'de verify
    edilemez), bu yüzden token'ı değiştirilmiş bir saldırgan farklı
    user bilgisi gösterebilir. auth/me zaten token doğruluğunu backend'de
    kontrol ediyor, ama getUser() senkron çağrılarda decode'a düşebilir.
    Kabul edilebilir trade-off (güvenlik kararı backend'de), ama not edilmeli.

3.6 [DÜŞÜK] redirectIfLoggedIn / requireAuth — open redirect riski
    auth.js:140-148 — redirectIfLoggedIn "index.html"e yönlendiriyor,
    hard-coded. Open redirect riski yok. AMA: Gelecekte query string
    ile redirect eklenirse dikkat edilmeli.

3.7 [DÜŞÜK] sessionStorage kullanımı yok
    auth.js + LoginRateLimitUI.js — localStorage kullanılıyor, sessionStorage
    hiç yok. Tasarım gereği session survive edilsin diye. Prompt 11.
    madde "localStorage güvenlik kaynağı değil" diyordu — bu bağlamda
    localStorage sadece UI state için kullanılıyor (LoginRateLimitUI'de
    artık hiç kullanılmıyor), auth.js'de token/user için kullanılıyor.
    Token için localStorage XSS riski (bkz 3.1).

7. RATE LIMIT BYPASS VEKTÖRLERİ
================================

7.1 [ORTA] Backend'in IP tabanlı olması — NAT/Proxy arkasında
    Backend LoginRateLimitingService IP'ye göre sayıyor. Aynı NAT/proxy
    arkasındaki birden fazla kişi aynı IP'yi paylaşır. Bir kişi 5
    yanlış deneme yaparsa tüm ağ 5dk bloklanır. Frontend bunu önleyemez
    (backend tarafı karar). Sadece not.

7.2 [DÜŞÜK] localStorage.clear() artık işe yaramaz (düzeltildi)
    Önceki kodda localStorage rate-limit kararını etkiliyordu (until
    timestamp). Yeni kodda localStorage hiç kullanılmıyor. Kullanıcı
    localStorage.clear() yaparsa UI state sıfırlanır, ama backend
    hâlâ rate-limit aktif. refreshLoginRateStatus tekrar backend'e
    sorup kilidi tekrar kurar. İYİ.

7.3 [DÜŞÜK] F5 / sayfa yenileme
    Yeni yapıda: sayfa yenilenince tüm in-memory state sıfırlanır, ama
    refreshLoginRateStatus init'te backend'e tekrar sorar. Backend
    rateLimited:true dönüyorsa UI tekrar kilitlenir. İYİ. F5 bypass
    mümkün değil (prompt 10. madde karşılandı).

7.4 [DÜŞÜK] Çoklu sekme → tek sekmede rate-limit aktifse diğer sekme
    etkilenmez
    Her sekme kendi backend response'unu alır. Sekme 1'de rate-limit
    aktifse, Sekme 2'de refreshLoginRateStatus yine aynı IP için
    rateLimited:true alır, UI kilitlenir. İYİ. (Bkz 6.1)
